## What I found

I went through both repos side by side for the first time. Summary before the questions, so the answers can be quick.

**Two repos, never pointed at each other.**

- `vip-web-frontend`, branch `feature/event-page` (pushed, draft PR). `/events` is built and renders, but every card comes from a hardcoded `EventItem[]` in `data/eventsData.tsx` — six bracketed placeholders. There is **no data-fetching layer anywhere in the repo**: no axios, no SWR, no TanStack Query, no `.env`, no `app/api/` route, not one `fetch()` call. That's deliberate — `CLAUDE.md` §6.8 says *"No CMS has been chosen yet, and Phase 1 does not add one. Do not install CMS SDKs, define CMS schemas, or add data-fetching layers now,"* with the goal that swapping a `data/<page>Data.tsx` content object for an API response later needs no component changes. That held: the swap is a data-source change, not a rewrite.
- `vip-web-backend`, `main` (PR #8 merged). Django 6.0.6 + DRF 3.17 + drf-spectacular. A real events CRUD API at `/api/v1/staff/events` with 21 passing API tests (26 in the suite), soft delete, a standard error envelope, and Swagger at `/api/docs/`.

**The two `Event` shapes do not line up.** Frontend `EventItem` is `components/modular_sections/EventCardGrid/types.ts:9-22`; backend `Event` is `events/models.py:8-48`, serialized at `events/serializers.py:9-21`.

| Card needs | Backend has | |
| --- | --- | --- |
| `title`, `description` | same | ok |
| `id` | `id` (UUID) | ok |
| `date` + `time` — **display strings** | `start_datetime` / `end_datetime` — real datetimes, `TIME_ZONE = "UTC"` | needs a formatting + timezone decision |
| `location` (**required** on the card) | — | **missing** |
| `organization` — the "Host:" row | — | **missing** |
| `audience` — the "For:" row | — | **missing** |

| `status` = a badge: "Open Registration", "Limited Seats", "Flagship" | `status` = `draft` / `published` / `archived` | **same name, different meaning** |
| `category` = "Event" / "Program" / "Workshop" / "Signature Event" | `category` = `general` / `challenge` / `community` | **no overlapping values** |
| `accent` (card border colour) | — | presentation — should stay code-side, not in the API |
| — | `event_type` = `workshop` / `webinar` / `conference` / `other` | no frontend counterpart |
| — | `slug` (unique, auto-generated) | unused — there is no `/events/[slug]` route |
| no image on cards; hero/featured/ATEC use images | no `ImageField`, no `MEDIA_ROOT`, no S3 config | affects the two `MediaFeature` sections |

**Four things currently block a browser from calling the API at all.** These aren't criticisms of the backend work — it's a clean, tested staff-tools slice. They're the gap between that and a public website reading from it.

1. **No CORS.** `django-cors-headers` is not in `requirements.txt`, `INSTALLED_APPS`, or `MIDDLEWARE`. A page served from Amplify cannot call this API today.
2. **No public endpoint.** Every route is under `/api/v1/staff/` and returns *all* non-deleted events regardless of `status`, with no filtering — so drafts would be served to the public.
3. **Nothing can be published.** `status` is in `read_only_fields` (`events/serializers.py:22`) and there is no `events/admin.py`, so the model isn't registered in Django admin. Nothing can move `draft → published` except a shell command.
4. **No authentication.** No `permission_classes`, no `authentication_classes`, no `is_staff` check anywhere in the repo. `/staff/` is only a URL string — the CRUD endpoints are open to anyone who can reach the host.

Also worth knowing: no pagination on the list endpoint, and `Dockerfile:19` runs `manage.py runserver` with no gunicorn and no `STATIC_ROOT`, so there's no production serving path yet. The backend README still describes the service as "Hello, World!" and lists DRF under "not yet implemented" — stale since PR #8.

**One thing I can't resolve on my own.** `origin/feature/payload-cms` — roughly 39,000 lines, unmerged since July 22 — embeds Payload CMS 3 in the frontend, connecting **directly to the same RDS Postgres** (in a separate `payload` schema). Its `CLAUDE.md` §5.5 already draws a boundary: Payload owns editorial page copy, Django owns business/application data. It does not say which side events fall on. Payload's `cms/blocks/EventCarouselBlock.ts` models events as an array inside one page rather than as a collection, so it can't really serve an events list — but the ownership call is the team's, not mine.

Worth flagging alongside it: the branch I'm working on still carries the §6.8 rule above, *"No CMS has been chosen yet."* The Payload branch deletes that line and replaces it with §5.5, *"an explicit, team-approved exception."* So the two branches give opposite instructions about whether a CMS exists, and I'd like to know which one is current.

Two details already line up nicely: the error envelope in `events/exceptions.py` matches the shape documented in the frontend `CLAUDE.md` §9 exactly, and the backend already uses `/api/v1/...` versioned routes as §9 expects.

## Questions

### §0 — Still open from Sept 21

None of the 18 questions in `docs/supervisor-questions_Sept_21.md` have been answered yet, so the Events page is still blocked on them. Carrying forward the five that matter most, because two of them now also decide a backend field:

1. **Hero buttons — "Innovation Hub Events" vs "Partner Events"**: scroll to two groups, two separate pages, or a filter preset? *This now also decides whether the Django model needs a hub/partner field.*
2. **What counts as a "Partner Event"** — hosted by a partner institution (CSUF, UT Dallas…), or industry partners only? *This decides which field the split keys on.*
3. **Where does Events sit in the nav**, and is it linked now or held until real content exists?
4. **Featured Signature Event + Programming at ATEC sections** — keep, or hide until there's real content?
5. **Are there any approved events at all** — even one — to replace the six placeholders?

### §A — Ownership (ask first; everything below depends on it)

6. **Are events editorial content or application data?** Payload models events as a per-page array; Django has a real table with a publish workflow. Which one owns event records?
7. **What's the status of `feature/payload-cms`** — merging, parked, or dropped? It's been sitting unmerged since July 22.
8. **If both ship**, is the split "Payload holds the page copy, Django serves the event records"? That means the Events page reads from two sources — is that acceptable?

### §B — The Event contract

9. **Adding the four missing fields** — `location`, `organization` (host), `audience`, and a registration URL (plus optional label and external flag) — to the Django model. Agreed? And does Esmeralda need any field beyond what's on the card today?
10. **The `status` collision.** Two different concepts share one name. Proposal: Django keeps `status` for the publish workflow, and the card badge becomes a separate `registration_status` field — or stays code-side entirely. Which?
11. **Controlled vocabularies.** Django has `category` (`general`/`challenge`/`community`) *and* `event_type` (`workshop`/`webinar`/`conference`/`other`). The design uses four categories (Event / Program / Workshop / Signature Event) and four audiences (Students / Educators / Community / Families). Reconcile to one list or keep two, and who owns the approved values?
12. **Dates and timezones.** Proposal: the API sends ISO datetimes in UTC, the frontend formats for display (Pacific). Confirm? Right now the page takes pre-formatted strings, which means nothing sorts and past events never auto-hide.
13. **Multi-day events.** Two placeholders say "[Approved Dates]", plural. One record with a start/end range, or separate records per day?
14. **Event images.** Add an `ImageField` + S3 storage now, or keep images code-side for Phase 1? Note `CLAUDE.md` §5.4 says the frontend must request the URL from the API and never construct S3 URLs itself.
15. **Detail pages.** The backend already generates unique slugs, but there's no `/events/[slug]` route and the design doesn't show one. Build detail pages, or stay a single grid?

### §C — API shape

16. **Add a public read endpoint** — `GET /api/v1/events`, published-only, upcoming first — separate from the staff routes? My recommendation is yes; the staff namespace shouldn't be what a public page calls.
17. **Pagination and filtering.** Should the public list paginate, and should `?category=` / `?audience=` be server-side? The page filters client-side today, which is fine for six events and not for sixty.
18. **Who publishes an event?** Today nothing can. Django admin, a staff PATCH that makes `status` writable, or Payload?
19. **Confirm the error envelope** `{code, message, details}` stays the contract — both repos already match, worth locking in.
20. **Trailing slashes.** Routes are registered without them (`events/urls.py:6-7`), which is unusual for Django. Lock the convention before the frontend hardcodes URLs.

### §D — Auth and access

21. **What authenticates the staff endpoints** — Django session, DRF token, JWT, or **Cognito**? The May AWS plan assumed Cognito; the Django backend has none of the above, and nothing is enforced right now.
